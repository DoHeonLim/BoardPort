# 직거래 약속 수락과 상품 상태 원자적 전환 트러블슈팅

## 문제 요약

BoardPort의 직거래 약속은 채팅 UI 안에서 제안되고, 수락되면 상품 상태까지 함께 바뀝니다.

즉, 이 기능은 단순히 `Appointment.status = ACCEPTED`로 끝나지 않고 동시에 다음을 만족해야 했습니다.

- 약속 상태 변경
- 상품 상태를 `예약 중`으로 전환
- 예약자 지정
- 다른 채팅방의 대기 약속 일괄 취소
- 시스템 메시지 생성
- 실시간 UI 반영

여기서 어느 한 단계라도 따로 처리하면 약속 상태와 상품 상태가 서로 어긋나는 정합성 문제가 생겼습니다.

## 1. 증상

### 1.1 같은 상품에 대해 둘 이상의 약속이 동시에 살아 있을 수 있음

여러 채팅방에서 같은 상품에 대한 약속이 동시에 제안되는 구조였기 때문에, 수락 시 다른 `PENDING` 약속을 정리하지 않으면 서로 다른 상대에게 "거래가 진행 중"처럼 보이는 문제가 생겼습니다.

### 1.2 상품 상태와 약속 상태가 어긋날 수 있음

약속은 수락됐는데 상품은 여전히 판매 중이거나, 반대로 상품은 예약 중인데 약속 상태가 여전히 대기 중으로 남는 불일치가 생겼습니다.

### 1.3 동시 요청 시 이중 예약 가능성

두 사용자가 거의 동시에 같은 상품의 약속을 수락하거나 예약자를 지정하면, 단순 순차 처리만으로는 이중 예약을 막기 어렵습니다.

## 2. 근본 원인

### 원인 A. 하나의 사용자 액션이 여러 엔터티를 동시에 바꿈

약속 수락은 다음 엔터티를 동시에 바꿉니다.

- `Appointment`
- `Product`
- `ProductMessage`
- `ProductChatRoom`

이 작업을 원자적으로 묶지 않으면 중간 단계 실패 시 비정상 상태가 남습니다.

### 원인 B. 같은 상품을 여러 채팅방이 공유

BoardPort의 상품 채팅은 상품 단위로 여러 방이 열릴 수 있습니다.
따라서 한 방의 약속 확정은 다른 방의 대기 약속에도 영향을 줍니다.

### 원인 C. 권한/참여자 상태와 거래 상태를 함께 검증해야 함

약속 수락은 단순히 "수신자가 버튼을 눌렀다"로 충분하지 않았습니다.

- 채팅방에 여전히 양쪽 참여자가 남아 있는지
- 차단 관계는 없는지
- 약속 시간이 이미 지나지 않았는지
- 상품이 이미 예약/판매 완료 상태는 아닌지

를 모두 같이 확인해야 했습니다.

## 3. 해결 전략

### 전략 1. 약속 수락을 단일 트랜잭션으로 통합

약속 상태 변경, 상품 예약 전환, 다른 약속 취소, 시스템 메시지 생성, 채팅방 최신화까지 하나의 DB 트랜잭션으로 묶었습니다.

### 전략 2. `updateMany` 조건으로 동시성 방어

`Appointment`와 `Product` 모두 현재 상태를 조건으로 둔 `updateMany`를 사용했습니다.

예:

- 약속은 `status === "PENDING"`일 때만 `ACCEPTED`
- 상품은 `purchase_userId === null && reservation_userId === null`일 때만 예약자 지정

이렇게 해서 동시에 두 요청이 들어와도 먼저 성공한 요청만 상태를 점유할 수 있게 했습니다.

### 전략 3. 같은 상품의 다른 대기 약속 일괄 취소

한 약속이 확정되면 같은 상품을 참조하는 다른 채팅방의 `PENDING` 약속들을 모두 `CANCELED`로 바꿨습니다.

### 전략 4. 실시간 UI는 트랜잭션 이후에만 브로드캐스트

DB가 확정된 뒤에만:

- `appointment_update`
- 시스템 메시지

를 Supabase Realtime으로 보내도록 분리했습니다.

여기서 Realtime 이벤트는 DB 상태를 확정하는 원본이 아니라, 확정된 결과를 각 클라이언트에 전파하는 후처리입니다.
따라서 브로드캐스트가 지연되거나 일부 실패해도 최종 판단 기준은 트랜잭션으로 확정된 DB 상태입니다.

## 4. 적용한 코드 변경

### 4.1 약속 제안 시 기존 대기 약속 정리

관련 파일:

- `appointment.ts`

핵심:

- 같은 채팅방의 기존 `PENDING` 약속은 새 제안 전에 모두 `CANCELED`
- 새 약속과 약속 제안 메시지를 트랜잭션 안에서 생성

### 4.2 약속 수락과 상품 예약 전환의 원자적 처리

관련 파일:

- `appointment.ts`

핵심:

1. 약속을 `PENDING -> ACCEPTED`
2. 상품을 `판매 중 -> 예약 중`
3. 예약자(`reservation_userId`) 지정
4. 다른 채팅방의 대기 약속 일괄 취소
5. 시스템 메시지 생성
6. 채팅방 `updated_at` 갱신

위 과정을 하나의 `db.$transaction()`으로 묶었습니다.

### 4.3 권한 / 나간 참여자·탈퇴 사용자 / 차단 관계 가드

관련 파일:

- `appointment.ts`
- `block.ts`
- `admin.ts`

핵심:

- 수락자 권한 확인
- 채팅방에 제안자와 수락자가 모두 남아 있는지 확인
- 차단 관계 여부 확인
- 약속 시간이 이미 지나지 않았는지 확인
- 제안/상태 변경 요청자는 정지 상태 여부도 별도로 확인

### 4.4 채팅 UI 반영

관련 파일:

- `AppointmentBubble.tsx`
- `ChatMessagesList.tsx`
- `useChatSubscription.ts`

핵심:

- 수락/거절 버튼 클릭 시 상태를 즉시 반영하는 낙관적 UI 적용
- 서버 확정 후 `appointment_update` 브로드캐스트로 모든 참여자 상태 동기화
- `ACCEPTED` 시 `router.refresh()`로 채팅 헤더의 상품 상태도 최신화
- 실패 응답을 받으면 약속 카드의 낙관 상태를 롤백

### 4.5 상품 상태 변경과 약속 상태 정합성 유지

관련 파일:

- `trade.ts`
- `status action`

핵심:

- 판매 완료 / 판매 중 복귀 시 관련 약속도 함께 정리
- 상품 상태 변경과 약속 상태가 서로 어긋나지 않도록 보정
- `SOLD -> SELLING` 복귀 시 예약자뿐 아니라 이미 구매자로 확정된 상대방에게도
  거래 취소 알림이 전달되도록 후속 보완
- 상품 상태 수동 변경도 `updateMany` 조건과 트랜잭션을 사용해 같은 상품의 `PENDING`/`ACCEPTED` 약속 상태를 함께 정리

### 4.6 약속 제안 드래프트 초기화

관련 파일:

- `ScheduleModal.tsx`

핵심:

- 약속 제안 모달을 닫거나 제출한 뒤 날짜, 시간, 장소, 지도 표시 상태를 초기화
- 취소된 약속 또는 이전 제안의 입력값이 다음 제안에 남지 않도록 처리
- 서버의 약속 상태 정합성과 별개로, 클라이언트 입력 드래프트도 매 제안마다 새 상태로 시작

## 5. 결과

### 수락 직후 상품 상태 정합성

- 약속이 수락되면 상품은 즉시 `예약 중`
- 예약자 정보도 함께 반영

### 다른 채팅방 대기 약속 정리

- 같은 상품의 다른 대기 약속은 자동 취소
- 중복 거래 진행 상태가 남지 않음

### 판매 완료 취소 시 구매자 알림 추가

- `예약 중 -> 판매 중`뿐 아니라 `판매 완료 -> 판매 중` 복귀에서도
  상대방(구매자)이 거래 취소 사실을 알림으로 확인할 수 있게 됨

### 동시 요청 방어

- 이미 처리된 약속은 다시 수락되지 않음
- 이미 예약/판매된 상품은 다시 예약되지 않음

### 재제안 UX 정리

- 약속을 취소하거나 모달을 닫은 뒤 다시 제안해도 이전 입력값이 남지 않음
- 사용자는 매번 새 날짜, 시간, 장소를 기준으로 약속을 제안

## 6. 설계에서 얻은 기준

### 6.1 약속 수락과 상품 예약을 함께 처리

약속 상태만 수락으로 바꾸면 상품은 판매 중으로 남을 수 있어, 두 상태를 같은 트랜잭션에서 변경해야 했습니다.

### 6.2 현재 상태를 조건으로 중복 수락 차단

현재 상태를 `updateMany` 조건에 포함하고 변경 건수를 확인해, 이미 처리된 약속이나 예약된 상품에 대한 수락 요청을 거절했습니다.

### 6.3 약속 수락 이벤트는 DB 커밋 이후 전송

약속 수락은 상품 예약과 함께 확정해야 하므로, DB 커밋 이후에 브로드캐스트합니다. 트랜잭션이 실패한 경우에는 수락 이벤트를 전송하지 않습니다.

### 6.4 거래 진행 여부는 상품 상태를 기준으로 판단

거래 진행·완료 여부는 서버 트랜잭션으로 확정된 상품 상태를 기준으로 판단합니다. 채팅방의 약속 상태만으로 거래 여부를 결정하지 않습니다.

## 7. 정리

약속 수락, 상품 예약, 다른 대기 약속 취소를 하나의 트랜잭션에서 처리하도록 변경했습니다. 현재 상태를 조건으로 중복 수락을 차단하고, 커밋 이후 실시간 이벤트를 전송합니다.
